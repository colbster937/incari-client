## Reading this backlog

- **It's the first layer.** TeaVM stops following calls at anything it can't resolve, so stubbing these items uncovers more. Rerun the survey after each round of porting work.
- **Call sites** are distinct (API, calling class, line) triples. Findings TeaVM reported inside JDK or class-library code are charged to the nearest game or library method that calls into it.
- **JDK classes TeaVM lacks.** Left alone, TeaVM would copy them from the JDK running the compile, dragging in JDK internals that can't work in a browser. The survey hides the host JDK, so each is listed where the game uses it.
- **Whole client, not one path.** Every class in the client jar is an analysis root, except the `no-root` packages in `tools/survey/rules.txt` (data generators, dedicated server). Code only the integrated server runs is included; singleplayer is deferred, but its code ships.
- **Stubs let the analysis continue.** TeaVM stops at anything missing, so the survey compiles in rounds, stubbing what each round reports, until nothing new appears. Stubbed items are still findings.
- **Full detail** (every call site with its method and line) is in `work/survey/26.3/findings.json` after a local run. It stays out of git because it names Mojang methods.
